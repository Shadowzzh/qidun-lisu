# 骊甦与 Deepexi 页面映射说明

## 文档目的

本文件用于说明当前骊甦官网与 Deepexi 参考站之间的页面映射关系，并给出下一阶段页面建设的推荐顺序。

本文件只回答两个问题：

- 骊甦当前页面体系与 Deepexi 页面体系之间如何对应
- 下一个最值得优先建设的页面是什么

## 判断前提

- 骊甦官网的业务内容以 `archive/` 为准
- 骊甦官网的当前实现以 `lisu-official-site/` 为准
- Deepexi 只作为多页门户结构、导航节奏和首页分工的参考

Deepexi 不是骊甦官网的逐页复刻模板。

## 总体结论

骊甦与 Deepexi 的关系，不是“页面 1:1 对位复刻”，而是“借用 Deepexi 的门户结构，再重组为骊甦自己的官网体系”。

最核心的参考关系是：

- 借 Deepexi 的多页门户策略
- 借 Deepexi 的首页总览与详情页承接分工
- 借 Deepexi 的导航节奏与科技感视觉方向
- 不直接继承 Deepexi 的产品命名、内容结构和资讯体系

## 页面映射总览

### 首页

- Deepexi：`/`
- 骊甦：`/`

这是当前最直接的一组映射。

两边首页都承担：

- 品牌入口
- 总览说明
- 核心内容摘要
- 向后续页面分发入口

区别在于：

- Deepexi 首页主要分发产品与资讯入口
- 骊甦首页当前和目标都更强调解决方案、能力、场景、案例与团队摘要

### 产品与能力承接页

- Deepexi：`/product/deepexi`、`/fastAgi`、`/product/deepSense`、`/product/dataSense`、`/product/deepClaw`
- 骊甦：`/solution`、`/capabilities`、`/capabilities/semantic-layer`、`/capabilities/data-platform`、`/capabilities/security`、`/capabilities/workspace`

这一组不是 1:1 页面映射，而是结构转译。

Deepexi 用多张产品页承接深内容。

骊甦的目标是：

- 用 `解决方案` 页承接整体论点
- 用 `能力页` 总览和能力详情页承接能力分层内容

也就是说，Deepexi 的“产品页簇”，在骊甦这里被拆成了“方案总览 + 能力体系”两层结构。

### 案例页

- Deepexi：`/case`
- 骊甦：`/cases`

这组映射的角色比较接近，都是承担案例与背书表达。

区别在于：

- Deepexi 当前更像一个案例展示页
- 骊甦目标里明确包含案例总览页和后续案例详情页

### 公司介绍页

- Deepexi：`/company`
- 骊甦：`/about`

这一组也属于角色对应，而不是路径照搬。

两边都承担：

- 公司介绍
- 团队背书
- 联系方式

但骊甦后续还会继续拆分：

- `/about/team`
- `/about/contact`

### 资讯与附属页

- Deepexi：`/news`、`/news-detail/*`、`/activity`、`/industry-report`、`/investor-relations`
- 骊甦：当前官方目标页体系中没有要求做对应的一期主页面

这部分不建议按 Deepexi 原样照搬。

原因是：

- 它们不属于骊甦当前一期核心闭环
- 文档中的主线是解决方案、能力、场景、案例、关于我们
- 先做资讯体系会分散建设重心

### 场景页

- Deepexi：无严格对应一级栏目
- 骊甦：`/scenarios` 及其子页

这是骊甦相对 Deepexi 更有差异化的一组页面。

它不是 Deepexi 的直接镜像，而是骊甦为了表达业务落地路径而新增强化的一级栏目。

这组页面后续会成为骊甦和 Deepexi 拉开内容差异的关键部分。

## 当前现状判断

当前 `lisu-official-site/` 的真实现状可以概括为：

- 真正已落地的只有首页原型
- 首页已经承担品牌、总览、入口和摘要内容
- 导航和页脚里已经出现一批待开放路径
- 整体页面节奏明显借用了 Deepexi 式门户结构

但当前代码现状还不能视为最终信息架构。

主要原因有三点：

- 当前多数导航路径仍是占位
- 当前部分路径命名还没有完全对齐官网权威文档
- 首页中已有不少本该由一级栏目页承接的内容入口，但对应页面还未真正落地

## 当前代码与目标架构的主要偏差

当前代码里已经出现了一些目标页意图，但命名和层级还没有完全收敛。

比较明显的偏差包括：

- 代码中存在 `/company`，目标文档中推荐的是 `/about`
- 代码中存在 `/semantic-layer`、`/data-platform`、`/security`、`/workspace`，目标文档中推荐的是 `/capabilities/*`
- 代码中的一级导航文字已接近目标架构，但栏目下的路径组织仍偏探索态

这说明当前项目已经从“单首页原型”进入了“准备展开多页结构”的阶段，但还没有真正跑通首页到一级栏目页的闭环。

## 下一页推荐

推荐下一个优先建设的页面是：

- `/solution`

## 推荐原因

### 原因一：它是一期优先页

当前官网权威文档已经明确，一期优先落地的页面包括：

- `/`
- `/solution`
- `/capabilities`
- `/scenarios`
- `/cases`
- `/about`

因此从页面优先级上看，`/solution` 本身就处于第一梯队。

### 原因二：它最适合承接当前首页已有的深内容入口

当前首页已经在表达下面这些内容：

- 为什么企业现在需要这套方案
- 企业级私有化 AI 知识智能平台的总体定位
- 七层架构总览
- 价值承诺
- 解决方案入口

这些内容如果继续都压在首页，会导致首页越来越像长方案文档。

`/solution` 正好可以承接这部分深内容，让首页回到“建立理解和导流”的角色。

### 原因三：它是后续能力页和场景页的上游页面

`/solution` 不是孤立页面。

它会为后续这些页面提供总论入口和结构前置：

- `/capabilities`
- `/scenarios`

先把 `解决方案` 页做好，后面再展开能力页和场景页，会更顺。

### 原因四：它最符合当前阶段的交付路线图

当前交付路线图建议的顺序是：

- 先建一级栏目结构
- 再建详情页承接体系

而 `解决方案` 页正是“一级栏目结构”里最关键的一页。

## 备选顺序

如果不是先做 `/solution`，两个次优先选项如下。

### 备选一：`/capabilities`

适合的情况：

- 希望优先把首页里的能力入口接到一个真实页面
- 希望尽快稳定能力信息分层

代价是：

- 方案总论页仍然缺位
- 首页里关于“为什么需要这套方案”的论点仍然没有正式承接页

### 备选二：`/scenarios`

适合的情况：

- 希望更快拉开骊甦与 Deepexi 的业务表达差异
- 希望先突出业务落地而不是平台结构

代价是：

- 会先建设业务侧页面
- 但整体方案主叙事和能力总叙事还不够稳

## 推荐建设顺序

综合当前文档、现状和依赖关系，推荐顺序如下：

1. `/solution`
2. `/capabilities`
3. `/scenarios`
4. `/cases`
5. `/about`

之后再继续展开二级详情页：

1. `/capabilities/semantic-layer`
2. `/capabilities/data-platform`
3. `/capabilities/security`
4. `/capabilities/workspace`
5. `/scenarios/supply-chain`
6. `/scenarios/finance`
7. `/scenarios/risk-control`
8. `/scenarios/customer-operations`

## 对后续任务的直接含义

- 如果下一步要写代码，最稳的目标页是 `/solution`
- 如果下一步先调导航，也应优先让导航路径逐步向 `/solution`、`/capabilities`、`/scenarios`、`/cases`、`/about` 对齐
- 首页后续不应继续无限扩写，而应把更完整的方案论点迁移到 `解决方案` 页

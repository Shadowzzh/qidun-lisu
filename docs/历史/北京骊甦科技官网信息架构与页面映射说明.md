## 文档职责

本文件只回答三个问题：

- 网站应该有哪些页面
- 每个页面各自负责解决什么表达问题
- `archive/ppt-source` 中的内容应优先落到哪些页面

本文件不负责：

- 页面模块顺序
- 组件命名或代码结构
- 当前阶段的实现优先级

## 站点结构建议

在保留现有目标站层级感的前提下，建议站点结构整理为：

```text
首页 -> /

解决方案
主方案总览 -> /solution
员工AI工作台 -> /workspace
算力底座 -> /infrastructure
知识语义层 -> /semantic-layer
AI数据平台 -> /data-platform
安全管控 -> /security

应用场景 -> /scenarios
行业洞察 -> /insights
案例中心 -> /cases
价值展望 -> /value
关于我们 -> /company
```

## 页面映射总原则

- 一个页面只解决一个主问题，不做并列主题的大杂烩。
- 首页负责总览与导流，不承担所有细节。
- 方案页和能力页负责解释“是什么”和“怎么构成”。
- 案例页负责证明“做过什么”和“怎么落地”。
- 弱支撑页面应主动收缩，不为了凑页数而重复其他页面内容。
- 路由可以继承原站层级，但页面语义必须服从当前资料，而不是反过来硬套原站栏目。

## 共享内容主承载规则

以下内容跨页复用频率高，必须先定义主承载页，避免重复失控：

- `slide-16.txt` 以 `/scenarios` 为主承载页；首页只做摘要入口，`/workspace` 只保留与工作台直接相关的场景映射。
- `slide-20.txt`、`slide-21.txt`、`slide-22.txt` 以 `/value` 为主承载页；`/solution` 和 `/insights` 可引用摘要，首页只保留一句话级别收束。
- `slide-24.txt`、`slide-25.txt`、`slide-26.txt` 以 `/cases` 为主承载页，不拆散到其他页面作为主体内容。
- `slide-27.txt`、`slide-28.txt`、`slide-29.txt` 同时服务 `/cases` 与 `/workspace`，但分工不同：
  - `/cases` 负责讲“客户案例中的落地结果”
  - `/workspace` 负责讲“工作台产品本身的能力结构”
- `slide-30.txt` 以 `/company` 为主承载页；首页只保留团队背书入口。

## 页面定义与来源映射

### `/`

- 页面名称：首页
- 页面职责：完成品牌识别、方案识别和页面分发
- 主问题：用户第一次进入网站后，能否在一个页面内理解“这是谁、解决什么问题、下一步看哪里”
- 主承载来源：`slide-01.txt`、`slide-04.txt`、`slide-05.txt`、`slide-07.txt`、`slide-10.txt`
- 辅助来源：`slide-16.txt`、`slide-22.txt`、`slide-24.txt`、`slide-27.txt`、`slide-30.txt`
- 支撑等级：强
- 注意事项：首页只做总览，不承接完整案例细节、完整三年展望和完整团队介绍

### `/solution`

- 页面名称：主方案总览
- 页面职责：集中回答“北京骊甦科技到底提供什么方案”
- 主问题：整套平台的定位、差异化和总体结构是什么
- 主承载来源：`slide-07.txt`、`slide-08.txt`、`slide-10.txt`
- 辅助来源：`slide-01.txt`、`slide-20.txt`、`slide-22.txt`
- 支撑等级：强
- 注意事项：这里应是全站最完整的方案全景页，但不替代具体能力子页

### `/workspace`

- 页面名称：员工AI工作台
- 页面职责：解释业务人员最终如何使用平台
- 主问题：这套平台如何变成可被员工使用的产品与工作入口
- 主承载来源：`slide-28.txt`、`slide-29.txt`
- 辅助来源：`slide-16.txt`
- 支撑等级：中
- 注意事项：该页要站在产品能力视角，不要写成“案例二复述页”

### `/infrastructure`

- 页面名称：算力底座
- 页面职责：解释平台运行的本地化算力与推理基础设施
- 主问题：平台跑在什么基础设施上，为什么能支撑企业级 AI 生产环境
- 主承载来源：`slide-11.txt`
- 辅助来源：`slide-25.txt`
- 支撑等级：强
- 注意事项：`slide-25.txt` 只作为案例中的落地印证，不应喧宾夺主

### `/semantic-layer`

- 页面名称：知识语义层
- 页面职责：突出整套方案最核心的差异化能力
- 主问题：为什么这套平台不是概率玩具，而是可解释、可审计的知识驱动系统
- 主承载来源：`slide-14.txt`
- 辅助来源：`slide-07.txt`、`slide-08.txt`
- 支撑等级：强
- 注意事项：该页应成为全站最清楚解释“方案灵魂”的页面

### `/data-platform`

- 页面名称：AI 数据平台
- 页面职责：解释数据如何被接入、治理、增强和开放
- 主问题：企业已有数据如何转化为可被平台使用的知识与能力
- 主承载来源：`slide-13.txt`、`slide-15.txt`
- 支撑等级：强
- 注意事项：重点是“业务系统不动，平台在其上语义贯通”，而不是罗列技术名词

### `/security`

- 页面名称：安全管控
- 页面职责：解释平台为什么适合企业核心业务
- 主问题：这套平台如何实现运维可观测、模型可管控、供应链可审计
- 主承载来源：`slide-12.txt`、`slide-17.txt`、`slide-18.txt`
- 支撑等级：强
- 注意事项：这里承担企业可信度证明，不应只停留在概念词汇展示

### `/scenarios`

- 页面名称：应用场景
- 页面职责：把方案能力翻译成业务价值落地
- 主问题：这套平台在供应链、财务、风控、客服运营等场景中能产生什么价值
- 主承载来源：`slide-16.txt`
- 辅助来源：`slide-10.txt`
- 支撑等级：中
- 注意事项：当前资料主要支持“场景方向”而非“完整案例细节”，页面深度需要控制

### `/insights`

- 页面名称：行业洞察
- 页面职责：承接“为什么现在必须做”这一层判断
- 主问题：企业为什么现在要建设私有化 AI 平台，以及晚做会失去什么
- 主承载来源：`slide-04.txt`、`slide-05.txt`
- 辅助来源：`slide-20.txt`、`slide-21.txt`
- 支撑等级：中
- 注意事项：这是观点整合页，不是新闻资讯页，也不是政策页

### `/cases`

- 页面名称：案例中心
- 页面职责：集中建立落地可信度
- 主问题：这套方案是否已经在真实企业场景中形成可理解的落地表达
- 主承载来源：`slide-24.txt`、`slide-25.txt`、`slide-26.txt`、`slide-27.txt`
- 辅助来源：`slide-28.txt`、`slide-29.txt`
- 支撑等级：强
- 注意事项：案例页要围绕“客户场景、落地结构、业务问题、能力映射”组织，而不是简单拼接附录页

### `/value`

- 页面名称：价值展望
- 页面职责：集中承接私有化价值、实施前提和中长期承诺
- 主问题：为什么值得做、做成的前提是什么、未来三年会走向哪里
- 主承载来源：`slide-20.txt`、`slide-21.txt`、`slide-22.txt`
- 支撑等级：弱
- 注意事项：这是典型的组合页，必须控制篇幅，避免和首页、`/solution`、`/insights` 形成大段重复

### `/company`

- 页面名称：关于我们
- 页面职责：完成品牌收束与团队背书
- 主问题：是谁在提供这套方案，以及为什么这支团队值得信任
- 主承载来源：`slide-30.txt`
- 辅助来源：`slide-01.txt`、`slide-22.txt`
- 支撑等级：中
- 注意事项：当前资料更强的是“团队背书”，不是“完整公司资料”，因此该页应避免伪装成信息齐全的标准企业介绍页

## 页面分层判断

### 强支撑页面

- 首页
- 主方案总览页
- 算力底座页
- 知识语义层页
- AI 数据平台页
- 安全管控页
- 案例中心页

这些页面在 PPT 中均有较直接的章节或成组内容支撑，适合作为首批稳定页面。

### 中支撑页面

- 员工AI工作台页
- 应用场景页
- 行业洞察页
- 关于我们页

这些页面能够成立，但依赖多页整合或语义转译，表达边界需要更谨慎。

### 弱支撑页面

- 价值展望页

该页依赖 `slide-20.txt`、`slide-21.txt`、`slide-22.txt` 组合成页，不适合无限扩写。

## 信息空缺提醒

当前资料中仍然缺少以下内容，因此对应页面能力需要主动降级：

- 标准新闻或动态体系
- 完整联系方式与表单字段
- 完整公司介绍、地址、资质、发展历程
- 可持续更新的行业内容资产

因此整站应优先被定义为“方案型官网”，而不是资讯型官网或上市公司官网。
